## 1. What I Built

A mobile-first MVP covering the one journey the case explicitly calls out — *"discover, plan and move toward purchasing"* — end to end:

**Launch** — a short animated intro (an amber ring draws itself around a train badge, the wordmark fades in, then the whole thing fades out) that overlays the real app while it's already loading behind it, rather than gating on it — see [§7](#7-apis--data-strategy).

**Home** — origin/destination search with a real station list, one-way/round-trip toggle, "Today / Tomorrow / This weekend" quick-date chips alongside the full date picker(s) (a return-date field appears for round trip, constrained to on-or-after the outbound date), passenger counts (with age bands, matching how Eurostar/Rail Europe actually price fares), a wheelchair-accessibility flag, quick-pick popular routes, and a full Turkish/English language toggle covering all UI copy, not just labels — see [§6](#6-tech-stack). Once you've run a search, up to 5 of them are remembered here too — see **Recent searches** below.

**Recent searches** — the last 5 distinct route + trip-type searches, persisted on-device so they survive closing the app (not just kept in memory), shown on Home with route, trip type and passenger count; tapping one re-runs it dated to today rather than replaying whatever date it was originally searched for, and each entry (or the whole list) can be removed. See [§7](#7-apis--data-strategy).

**Results** — a date strip showing the cheapest fare for nearby days, with the single cheapest day in the visible window highlighted so users can shop by date before committing, a per-departure list with three fare classes (Standard / Plus / Premier) shown side by side, sold-out/low-availability signals, a live EUR→TRY/USD/GBP currency toggle, and fare-conditions detail sheets. Departure times are Eurostar's own real, scheduled times when a live feed of them is available for that route/date (marked with a "Canlı" badge, plus any reported delay), and a clearly-labelled synthetic fallback otherwise — see [§7.6](#7-apis--data-strategy). For a round trip, this same screen is used twice — Outbound, then Return — mirroring the step pattern I found on the real eurostar.com booking flow during research, with a link back to revise the outbound pick before continuing.

**Checkout / handoff** — a trip summary (both legs, and a combined estimated total, for a round trip) and a "Continue on eurotrain.net" action that deep-links out to eurotrain.net's real, live search-results page for the same origin, destination, date(s) and passenger count — so the traveller sees genuine current prices and completes the actual purchase on that real site, round trip included in a single link. No payment form, no card data, no account, ever touches this app. See [§7](#7-apis--data-strategy) for why this is the checkout model, not a mocked payment form, and for why the redirect target is eurotrain.net rather than eurostar.com.

**Confirmation / handoff summary** — reiterates the trip (both legs for a round trip), makes clear no booking or charge happened in-app, and offers to reopen eurotrain.net or start a new search.

**Help & contact** — a dedicated screen, reachable from a "?" button on Home, with an in-app FAQ covering what a reviewer is most likely to wonder about (why prices look like demo data, why there's no in-app payment, what the "Canlı" badge means, how round trip works, how to switch language, what the no-connection screen means), plus links out to eurotrain.net's own real help center and contact form — not an invented support inbox this app never had. See [§7](#7-apis--data-strategy).

**No-connection gate** — the whole app sits behind a full-screen "İnternet bağlantısı yok" (no internet connection) state whenever the device has no usable connection, both at launch and if connectivity drops mid-session, with a "Tekrar dene" retry action and automatic recovery once back online. See [§7.5](#7-apis--data-strategy).

Loading, empty ("no direct route" / "no departures that day") and error (simulated network failure with retry) states are implemented on the two screens where they matter most, rather than only on the happy path.

I did **not** build: authentication/accounts, a "My Bookings" area, multi-leg/interline journeys, seat maps, or in-app payment collection. See [§3 Product Scope](#3-product-scope--prioritization) for why.

## 2. Quick Start

```bash
npm install
npx expo start          # then press "w" for web, or scan the QR code with Expo Go
```

Web build used for automated testing during development:

```bash
EXPO_OFFLINE=1 npx expo export --platform web   # -> dist/, serve with any static server
```

(`EXPO_OFFLINE=1` is only needed in network-restricted CI/sandbox environments where Expo's own update-check call is blocked — see §7.)

**Optional one-time step, to turn on real live departure times (§7.6):** the app works immediately without this — it just shows the clearly-labelled synthetic schedule until you do it.

1. Push this repo to your own GitHub repo (a normal `git push`, nothing special).
2. Open `src/services/liveScheduleService.ts` and change the one line:
   ```ts
   const LIVE_SCHEDULE_REPO = 'YOUR_GITHUB_USERNAME/YOUR_REPO_NAME';
   ```
   to your actual `owner/repo`, e.g. `'nihatcuhacii/eurotrain-mvp'`.
3. That's it — nothing to deploy or sign up for. The `refresh-schedules` GitHub Actions workflow starts running automatically on its own schedule (every 15 minutes) as soon as the workflow file is on GitHub. Check progress under the repo's **Actions** tab; to trigger a run immediately instead of waiting, open the "Refresh live schedules" workflow there and click **Run workflow**.
4. Once the first run finishes, `https://raw.githubusercontent.com/<owner>/<repo>/data/live-schedules.json` is live, and Results will start showing real departure times (a "Canlı" badge) for the routes/dates the feed covers.

## 3. Product Scope & Prioritization

The brief deliberately withholds a feature list, so here's the reasoning behind what's in vs. out.

**In scope**, because it *is* the core value proposition ("discover, plan, move toward purchasing"):
search with a real station set and sensible passenger/accessibility inputs; one-way **and round-trip** search, since a return leg is one of the most common real-world trip shapes and the real eurostar.com treats it as core, not an add-on (confirmed by walking its live "Add return" flow during research); comparing price across dates and fare classes (this is the single biggest UX differentiator on the real eurostar.com — I verified this by walking their live site before designing this MVP, see `eurostar-analiz.md`); real, live-refreshed departure/arrival times and delay status sourced from Eurostar's own open GTFS feed, not just illustrative slots (§7.6); a checkout/handoff step that hands the traveller to a *real, live* eurostar.com search for the exact trip they configured, so "move toward purchasing" ends at an actual, bookable page instead of a fake success screen.

**Deliberately left out**, and why:

- **Accounts / login / loyalty (Club Eurostar-style points)** — real value, but orthogonal to proving the core booking journey works. A guest, click-out flow already demonstrates the "purchase" step end-to-end.
- **Seat selection / seat maps** — high implementation cost, low signal for a product-thinking exercise; Standard/Plus/Premier class selection already demonstrates the pricing-tier UX.
- **Multi-leg / connecting journeys** (e.g. London → Cologne via Brussels) — the real Rail Europe network supports this, but it roughly doubles the pricing-model complexity for a case that rewards *focus*.
- **In-app payments** — explicitly out of scope per the brief (§4/§6 of the case); rather than mock a fake payment form, the MVP hands off to eurotrain.net's own real, secure checkout instead (§7).
- **Push notifications for live train status** — genuinely valuable (it's the #1 reason Eurostar's own app exists, per their marketing copy), but needs a backend/notification service that doesn't add product-decision signal here.

## 4. Core User Journey

One-way: Home → Results → (select fare) → Checkout (summary + handoff) → Confirmation (handoff summary), with exactly one required decision per screen (where to go, when/which fare, continue to eurotrain.net). Round trip: the same flow with one extra decision — Results is used for Outbound, then Return, before Checkout — matching the Outbound → Return → Checkout breadcrumb I found on eurostar.com's own booking flow during research, rather than inventing a different pattern. The trip summary is always visible once a fare is selected (a sticky bottom bar), mirroring the pattern I observed being effective on eurostar.com — the user always knows what trip they're about to continue with before leaving the app.

## 5. UX/UI Thinking

- **Information hierarchy**: price and time are the two things a rail traveller scans for first, so both get the largest type on the results list; everything else (duration, luggage rules, seats-left) is secondary.
- **Feedback**: every async action (searching, paying) has a visible loading state; the results date-strip updates immediately on tap so date-shopping feels instant.
- **Empty/error states are first-class**, not an afterthought: an invalid origin/destination pair disables the search button *and* explains why (bad request should never be reachable); a simulated network failure on Results shows a retry action instead of a blank screen; a date with no departures says so instead of showing an empty list.
- **Currency fallback is visible, not silent**: when the live FX call fails, the UI says so ("live" vs "cached" badge) instead of pretending the number is fresh.

## 6. Tech Stack

| Layer | Choice | Why |
|---|---|---|
| Framework | React Native + Expo (TypeScript) | One codebase → iOS/Android/web; Expo's managed workflow removes native-build overhead, which matters for a 4-6h case; large hiring pool overlap with a JS/TS-heavy product org. |
| Navigation | React Navigation (native-stack) | De facto standard, native performance, small API surface for 4 screens. |
| State | React Context (`AppState`) | The shared state (search criteria, selected fare) is small and shallow — Redux/Zustand would be unjustified overhead at this scope. Documented as a conscious choice, not an oversight. |
| Styling | `StyleSheet` + a small hand-rolled token system (`src/theme`) | No design-system dependency to install/learn; tokens keep colors/spacing consistent and swappable. |
| Data | Local TypeScript modules (`src/data`, `src/services`) | See §7. |
| Connectivity | `expo-network` (`NetworkGate`, `useNetworkStatus`) | Official Expo module, zero native config in the managed workflow; reflects real device/browser connectivity rather than being simulated. See §7.5. |
| Localization | Hand-rolled i18n (`src/i18n/translations.ts`, `useTranslation`) | A single `Strings` TypeScript interface both the `tr` and `en` dictionaries must satisfy, so a missing translation is a compile-time error, not a silent runtime fallback to the wrong language; no library needed for 2 languages. |
| Local persistence | `@react-native-async-storage/async-storage` (`src/services/recentSearches.ts`) | The app's only genuinely persisted state (recent searches, §7.7) is isolated in its own storage-backed service rather than folded into `AppState`'s in-memory context, since it's the only thing that needs to survive an app restart. |
| Live schedule pipeline | Plain Node.js script (`scripts/fetch-live-schedules.mjs`) on a GitHub Actions schedule, output served from a `data` branch via `raw.githubusercontent.com` | No server to run or pay for; sidesteps Cloudflare Workers' free-tier 10ms-CPU-per-invocation limit, which a GTFS-zip-parsing job would blow through. See §7.6. |

## 7. APIs & Data Strategy

This is the decision I want to be most explicit about, because the brief specifically asks for it.

**Rail Europe's real booking/pricing API is not reachable for this case.** Odamigo holds that integration as a B2B partner relationship — it's not a self-service API a candidate can sign up for in a few days. Attempting to reverse-engineer or scrape eurostar.com's live search as a backend was considered and rejected: it would violate their terms of use, is brittle (breaks on any front-end change), and is exactly the kind of production-readiness red flag the case's evaluation criteria call out.

**What I did instead — a hybrid:**

1. **Real, static reference data** (`src/data/stations.ts`, `src/data/routes.ts`): actual Eurostar-network station names, cities, countries and coordinates, plus route durations and fare ranges gathered by manually browsing live search results on eurostar.com (documented separately in `eurostar-analiz.md`, produced as research before this build). This is not live data and does not claim to be — it's a realistic, honestly-sourced seed set.
2. **A deterministic pricing engine** (`src/services/journeyGenerator.ts`): fares are derived from a seeded hash of route+date+time-slot, not `Math.random()`. Same search always returns the same result, which makes the app demoable and testable, while still producing believable day-to-day and lead-time-based price variation (weekend/last-minute markup, occasional sold-out fare classes) — patterns I observed on the real site.
3. **One genuinely live, external API** (`src/services/currencyService.ts`): EUR→TRY/USD/GBP conversion via `frankfurter.app` (free, keyless, ECB-backed). This is real, not mocked — chosen because Odamigo's core markets are Türkiye, Cyprus and Azerbaijan, so showing a EUR fare converted to TRY is genuine product value, not a demo flourish. It's called with a 4s timeout and falls back to a hard-coded rate snapshot on failure, with the UI honestly labelling which one is showing. (In the sandboxed environment this was built in, outbound network is allow-listed to package registries only, so the live call fails there by design and you'll see the fallback path — it will succeed on a normal device or CI runner with open internet.)
4. **A real deep-link handoff at checkout** (`src/services/bookingLink.ts`): rather than fake a booking, the Checkout screen builds a URL into eurotrain.net's actual search-results page — `https://eurotrain.net/tr/search?origin=<country>:<slug>&destination=<country>:<slug>&date=<date>T06:00:00&adults=<n>&youths=<n>&seniors=<n>&children=<n>&tripType=oneway` (round trip sets `tripType=roundtrip` and adds a single `&returnDate=<date>` to the *same* URL — eurotrain.net's own round-trip search results page works that way too, confirmed by walking a real round-trip search on the live site rather than assumed) — using the same origin, destination, date(s) and passenger counts the user configured, and opens it via `Linking.openURL`. The `origin`/`destination` values are eurotrain.net's own internal country-code + booking-slug pairs (`Station.bookingSlug` in `src/data/stations.ts`), captured by hand by walking real search results on the live site — there's no public station-lookup API to pull them from programmatically. (One real-world wrinkle handled here: Disneyland Paris has its own booking slug, `marne_la_vallee_chessy`, distinct from Paris Gare du Nord's `paris`, even though both are "Paris" stations — verified on the live site rather than assumed.) eurotrain.net's passenger picker also has no separate "infant" fare band, so `passengers.infant` is deliberately not sent, rather than mapped somewhere it doesn't belong. This is the metasearch/click-out pattern Skyscanner and Google Flights use: compare in-app, buy on the real provider's site. It means the *prices you compare in-app are illustrative (§7.1/7.2), but the purchase you can actually complete is 100% real* — genuinely different from, and a stronger answer to "how real is this" than, either pure mock data or a scraped/faked booking API. **Why eurotrain.net and not eurostar.com**: the redirect target was changed after the initial design to eurotrain.net, another real, live booking site serving the same Eurostar/Thalys network, and the same click-out model and research-first verification approach carried over unchanged — only the URL scheme and station identifiers needed re-deriving from the new site. (Note the naming overlap with this app's own name is coincidental: eurotrain.net is an independent third-party site, not affiliated with this project; copy elsewhere in the app is deliberately worded — "this app" rather than "EuroTrain" wherever it could be confused with the redirect target — to keep the two distinct for anyone reading closely.)
5. **A real connectivity check gating the app** (`src/hooks/useNetworkStatus.ts`, `src/components/NetworkGate.tsx`): the whole app is wrapped in a gate that reads the device's actual network state via `expo-network` (`navigator.onLine` + its `online`/`offline` events on web; OS-reported reachability on native) and shows a blocking "no internet" screen — with a manual retry and automatic recovery — whenever there isn't one. This isn't simulated: it reflects the real device/browser connectivity state, both at launch and if it changes mid-session. I chose to gate the *whole* app rather than only Checkout because Results' local pricing (§7.1/7.2) would technically still render offline, but letting someone search and pick a fare only to find "Continue on eurotrain.net" doesn't work is a worse experience than failing loudly and early. One acknowledged limitation: like any `navigator.onLine`-based check, it reflects "connected to a network," not "the internet is actually reachable" (e.g. a Wi-Fi captive portal with no real internet reads as online) — see §12.
6. **Real, live-refreshed departure times and delays** (`scripts/fetch-live-schedules.mjs`, `src/services/liveScheduleService.ts`): Eurostar/Thalys publish an official open GTFS + GTFS-RT feed (schedules + real-time delay/platform data), free and keyless under France's Licence Ouverte 2.0 — [transport.data.gouv.fr/datasets/eurostar-gtfs-plan-de-transport-et-temps-reel](https://transport.data.gouv.fr/datasets/eurostar-gtfs-plan-de-transport-et-temps-reel). This is genuinely live train-schedule data, not seed data, and it's a different thing from points 1–2 above: those model *prices*, which the GTFS feed doesn't publish at all (fares/inventory are still the unreachable Rail Europe partner API). Architecture, since it matters for "how live is live": a GitHub Actions workflow (`.github/workflows/refresh-schedules.yml`) runs on a schedule, downloads + parses the GTFS static/real-time feeds in plain Node.js, and publishes a compact `live-schedules.json` to this repo's `data` branch as a single rolling commit; the app fetches that file straight from `raw.githubusercontent.com` with a short timeout and an in-memory cache. I initially planned a small Cloudflare Worker for this, but researched Cloudflare's free-plan limits before building it and found a hard **10ms CPU-time cap per invocation, including on Cron Triggers** — nowhere near enough to unzip and parse a multi-MB GTFS feed — so I pivoted to GitHub Actions instead, which has no such trap and needs no new hosting account. Real departures are marked with a "Canlı" badge in Results and priced through the exact same deterministic engine as synthetic ones (point 2); when there's no live coverage for a given route/date (feed unreachable, not yet configured, or a connecting journey this feed doesn't model — see §12), it falls back to the synthetic generator exactly as before, with the UI honestly labelling which one is showing (mirroring point 3's live/fallback badge pattern). **One-time setup required**: `LIVE_SCHEDULE_REPO` in `src/services/liveScheduleService.ts` ships as a placeholder — see §2 Quick Start for the one line to change after pushing this repo to your own GitHub.

7. **On-device persistence for recent searches** (`src/services/recentSearches.ts`, `@react-native-async-storage/async-storage`): everything else in this app's shared state (search criteria mid-session, selected fare, in `state/AppState.tsx`) lives only in memory and is intentionally lost on app close, since none of it needs to survive a restart. Recent searches are different — surviving a restart is the whole point — so they're isolated in their own storage-backed service rather than folded into `AppState`. Deliberately *not* stored: the date/return-date that was searched, since a saved date is almost always stale by the time it's revisited — re-running a saved entry always re-dates it to today instead of replaying a past date (§1). Entries are capped at 5, deduped by route + trip-type (re-running a search moves it to the top instead of duplicating it), and every read/write is wrapped in a try/catch so a storage failure degrades to "no recent searches" rather than crashing the app.

**Trade-off, stated plainly**: fare *prices* shown while browsing in this app are illustrative, not real (points 1–2 above) — that hasn't changed. What has changed is that the *departure times themselves* are now real where the live feed has coverage (point 6), not just illustrative slots. Checkout was already not a fake success screen; it hands off to a real, live, bookable page on eurotrain.net, which remains the one place in the funnel where "is this real" matters most for price. In exchange for pricing still being modelled, the app needs no payment-related API-key/secret management surface, and every screen state (including sold-out and error states) is reachable on demand for a demo rather than dependent on real-world timing.

## 8. Architecture

```
App.tsx                    entry: providers (gesture handler, safe area, app state) + network gate + navigator,
                             with SplashIntro overlaid on top while the app underneath is already loading (§1)
src/
  navigation/               React Navigation stack + route param types
  screens/                  one file per screen, composed from components (incl. HelpScreen)
  components/               presentational + modal components, no business logic (incl. NetworkGate, SplashIntro)
  services/                 journeyGenerator (pricing), currencyService (FX), bookingLink (checkout deep-link, §7.4),
                             liveScheduleService (real GTFS-sourced departures, §7.6), recentSearches (on-device
                             persistence, §7.7)
  state/                    AppState — cross-screen search/selection context (in-memory only, §7.7)
  hooks/                    useExchangeRates, useNetworkStatus, useRecentSearches, useTranslation
  i18n/                     translations.ts — the TR/EN string dictionary (§6)
  data/                     stations.ts, routes.ts, fareClasses.ts — the seed dataset
  theme/                    design tokens
  types/                    shared TypeScript interfaces
scripts/                    fetch-live-schedules.mjs (+ gtfs-lib.mjs, its test) — plain Node.js, outside the
                             app bundle entirely; run by GitHub Actions, not by the app (§7.6)
.github/workflows/          refresh-schedules.yml — the scheduled pipeline that runs scripts/ and
                             publishes live-schedules.json to the `data` branch
```

Screens own layout and user interaction; components are reusable and presentational; services own all business/data logic and are the seam where a real backend would plug in later (see §12). This separation is the main thing making "swap mock data for a real API" a services-layer change rather than a screen rewrite — `liveScheduleService.ts` is a working example of exactly that swap already having happened for schedules, with the same pattern ready for `journeyGenerator.ts`'s pricing once a real fares API is reachable.

## 9. AI-Assisted Development

Built end-to-end with Claude (Sonnet) as a pair-programmer inside an agentic coding environment (Claude Code / Cowork). Concretely:

- Product framing and scope decisions (§3) were reasoned through in conversation before any code was written, anchored on the actual case brief and on hands-on research of the real eurostar.com booking flow (browser automation was used to walk the live site — search, fare selection, checkout, account, loyalty program — to ground the seed data and UX patterns in something real rather than invented).
- All application code (types, data, services, components, screens, navigation) was AI-generated, then verified by me by actually running it: `tsc --noEmit` for type-safety, `expo export --platform web` to confirm the Metro bundle builds cleanly, and a scripted Playwright walk-through of the full Home → Results → Checkout → Confirmation flow (including the error/retry and no-route-warning states) against the exported build, with console/page errors asserted empty.
- One real bug this caught and I fixed: a `react`/`react-dom` version mismatch (19.2.3 vs 19.2.0) that crashed the app at runtime with a minified React error — invisible from source review or type-checking alone, only caught by actually loading the page in a browser and reading the console.
- The checkout deep-link (§7.4) was built the same way: browser automation walked the real eurostar.com search form for each of the 9 seed stations to capture their actual internal station ids, then the resulting URLs were verified by re-running the Playwright walk-through with network interception on `eurostar.com`, asserting the constructed deep-link's `origin`/`destination`/`outbound`/`adult` query params exactly matched the search criteria the user configured — not just that a link opened.
- The connectivity gate (§7.5) was checked against the actual current `expo-network` package (matching this project's Expo SDK version) rather than from memory, since Expo's APIs change between versions; I read the installed package's own TypeScript definitions and web-platform source to confirm exactly how `isConnected`/`isInternetReachable` behave (including a web-specific quirk in the docs' generic wording that the source clarified). It was then verified against three scenarios in Playwright: a normal online launch (gate absent), the app already running when connectivity drops and then recovers (gate appears, then disappears), and a simulated offline launch (gate appears immediately) — the latter required care, since naively blocking all network traffic at launch also prevents the page's own script from loading, which isn't representative of a real native app whose JS bundle is already on-device before any connectivity check runs.
- Round-trip search was added the same research-first way: rather than guess how eurostar.com structures a round-trip URL, browser automation ran an actual round-trip search on the live site (London → Paris, with a return date) and read the resulting URL, which is what showed the real pattern is a single `inbound=<date>` param alongside `outbound=<date>` on the same search-results URL — simpler than the two-separate-searches design I'd otherwise have guessed at, and it also surfaced the real site's own Outbound → Return step pattern, which the in-app Results screen now mirrors. I also found and fixed a pre-existing latent bug while wiring this up: `findRoute()` looked up a route by either direction but returned it in its originally-stored orientation, which would have shown an outbound-looking direction on what should've been the return leg; fixed by having it re-orient the returned route to match the direction actually requested. Verified with `tsc --noEmit`, an offline web export, a full round-trip Playwright walk-through (toggle trip type → outbound selection → return selection → checkout showing both legs and a combined total → confirmation → deep-link params asserted to include both `outbound` and `inbound`), and a re-run of the original one-way walk-through to confirm no regression (no `inbound` param leaks into a one-way link).
- Live schedule integration (§7.6) followed the same research-before-code discipline as the rest of the project, and included one real architecture course-correction: I asked whether a system existed for genuinely live journey data, researched and found Eurostar's official open GTFS/GTFS-RT feed (rather than assuming one didn't exist or reaching for a scrape), and initially scoped the backend as a small Cloudflare Worker. Before writing it, I looked up Cloudflare's actual current free-plan limits and found a 10ms-CPU-per-invocation cap that applies to Cron Triggers too — not enough to unzip and parse a multi-MB GTFS feed — so I pivoted to a GitHub Actions workflow instead and said so explicitly rather than quietly building something different from what was agreed. The parsing/matching logic (`scripts/gtfs-lib.mjs`) was unit-tested (`node --test`) against a small hand-built synthetic GTFS fixture, not the real feed, since this sandbox's outbound network is allow-listed to package registries only and the real Eurostar host returns HTTP 403 from here (confirmed with `curl -sI`, same restriction already documented for `frankfurter.app` in §7.3) — the fixture exercises the identical stop-matching/service-date-resolution/delay-merge code paths a real feed would. End-to-end app behavior was then verified with Playwright against the exported web build in two configurations: the real (blocked-in-sandbox) URL, confirming the app fails closed to the synthetic fallback without crashing or hanging; and a mocked live-schedules.json via Playwright route interception, confirming the "Canlı" badge, per-journey delay text, and header freshness line all render correctly when live data *is* available — since the actual GTFS host can't be reached from this sandbox, this mock was the only way to verify that code path before hand-off.
- **Full TR/EN localization** (§6) was added the same research-and-verify way: a hand-rolled `src/i18n/translations.ts` with a single `Strings` TypeScript interface both the `tr` and `en` dictionaries must satisfy, so a missing translation is a compile-time error rather than a silent fallback to the wrong language at runtime. Building it surfaced a real pre-existing bug: fare-class descriptions/benefits (`fareClasses.ts`) were hard-coded English-only text, so even a Turkish session was showing English copy there — fixed by making that data language-aware too. Adding the "Today/Tomorrow/This weekend" quick-date chips on Home in the same pass caught a second real bug: keying each chip by its computed date broke when two presets landed on the same date (e.g. if today is a Friday, "Tomorrow" and "This weekend" resolve to the same date), which meant two list items shared a React `key` and reconciliation silently highlighted the wrong chip on tap — caught by a Playwright script that asserted the DOM's actual highlighted-element color rather than just taking a screenshot, and fixed by keying each chip by a stable preset id instead of the date it resolves to.
- The checkout redirect target was later changed from eurostar.com to eurotrain.net (§7.4), and the same research discipline applied unchanged: rather than assume the new site's URL scheme or station identifiers matched the old one, browser automation drove eurotrain.net's own live search form for each of the 9 seed stations (including confirming Disneyland Paris uses its own booking slug, distinct from Paris Gare du Nord's), then a Playwright script with network interception on eurotrain.net re-verified the constructed deep-link's query parameters exactly matched the search criteria configured — the same way the original eurostar.com link had been verified, not just re-pointed at a new domain and assumed to still work.
- Recent searches (§1, §7.7) were built with the same "verify by running it" discipline: `@react-native-async-storage/async-storage` was installed at the exact version this project's Expo SDK expects (read from `node_modules/expo/bundledNativeModules.json`, since `npx expo install` isn't reachable from this sandbox — see below), the persistence service was written with every read/write wrapped so a storage failure can't crash the app, and the feature was verified end-to-end with Playwright: run two searches, confirm both appear on Home in most-recent-first order, tap one and confirm it re-navigates with the right criteria, remove one and confirm only it disappears, clear all and confirm the section itself disappears. Adding the package itself hit a real environment limitation worth naming: `npx expo install <package>` fails in this sandbox behind a proxy restriction on Expo's own compatibility-check API, so the exact SDK-recommended version was read directly out of Expo's own manifest and installed with plain `npm install` instead, then re-verified with a clean `npm ci`.
- The Help & contact screen (§1) links out to eurotrain.net's real help center and contact form rather than inventing a support inbox this app never had — the two URLs were found by navigating eurotrain.net's own site with browser automation and reading its actual help/contact links, the same verify-before-trusting approach used for every other external integration point in this project, rather than guessed from a common URL pattern.
- AI as an **end-user-facing feature was deliberately not included**. The obvious candidate would be a chat assistant (the real eurostar.com has one — "Ask AI" — which I saw during research). I left it out because it would add UI surface without adding signal about the core booking journey this case asks for; it's called out explicitly as future work in the roadmap instead.

## 10. Assumptions

- "MVP" targets an individual leisure/business traveller booking directly, not Odamigo's B2B travel-agency customers (a materially different, permissions-heavy product).
- Fare rules text (exchange/refund/luggage policy) is paraphrased from what's publicly displayed on eurostar.com's real fare-conditions panel, not copied verbatim, and is illustrative rather than legally binding copy.
- Only the 14 routes in `src/data/routes.ts` are "servable" — searching an unconnected pair correctly shows a "no direct route" state rather than crashing or inventing a route. All 9 seed stations have a real eurotrain.net `bookingSlug` (§7.4), so every servable route can deep-link out correctly.

## 11. Security & Production Considerations

Per the brief, production-grade auth/payments/security hardening was intentionally not built. The checkout-as-deep-link model (§7.4) actually simplifies this story considerably — the app never collects payment or passenger PII at all, so most of the classic booking-app risk surface doesn't exist here by construction, not just by omission. What exists today and what a real launch would need:

| Area | Current state (MVP) | What production needs |
|---|---|---|
| Payments | Not handled at all — checkout hands off to eurotrain.net's own real, secure checkout via deep link; this app never sees card data | If a future version processed payment in-app (e.g. for an Odamigo-branded checkout instead of a redirect), it would need a PCI-DSS-scoped PSP integration (Stripe, or iyzico given the TR/CY/AZ market) using hosted fields/tokenization, 3-D Secure, webhook-driven confirmation, and idempotency keys against double-charging. |
| Auth | None — no account, no login | Real auth would need secure token storage (not AsyncStorage for anything sensitive), refresh-token rotation, and rate-limited login to resist credential stuffing. |
| Local storage | `@react-native-async-storage/async-storage` holds only recent-search shortcuts (route ids, trip type, passenger counts, §7.7) — no name, payment, or account data ever touches it | Already the right pattern for this data; a future auth feature would need a separate, more secure store (Keychain/Keystore via `expo-secure-store`), not this one, per the Auth row above. |
| Secrets | None in the client — the one real API call (FX rates) needs no key | Any real backend/API key must never ship in the client bundle; use a thin backend-for-frontend to hold secrets and proxy requests. |
| Personal data | None collected or stored — search criteria (route, date, passenger counts) live only in memory for the session and are never transmitted anywhere except as non-identifying query params in the eurotrain.net deep-link itself (route/date/passenger-count, no name/email/payment info); recent-search shortcuts (§7.7) are the one thing that persists on-device, and are equally non-identifying | If a future version added accounts or in-app booking, it would need GDPR/KVKK-compliant handling: encryption at rest, defined retention periods, explicit consent capture, data-subject deletion support. |
| Reliability | Simulated latency/failure only on the in-app search/results side; the deep-link handoff depends on `Linking.openURL` succeeding, with a user-facing error alert if the OS can't open it | Real integration needs retry/backoff and circuit-breaking around the Rail Europe partner API (if search/results were ever backed by it), and monitoring/alerting on handoff-link failure rates. |
| Live schedule pipeline | No secrets required — `refresh-schedules.yml` uses only the default, auto-scoped `GITHUB_TOKEN` (`contents: write`, this repo only) to publish to the `data` branch; the data itself (train times) is public, non-personal information from an open feed | If a paid/authenticated data source ever replaced the open GTFS feed, its key would need to live in GitHub Actions Secrets (never in client code or the repo) and the app would need a thin proxy rather than fetching a provider's API directly from the client. |
| Input validation | N/A — no form fields collect user data in-app anymore | If forms are reintroduced later, client-side validation must always be re-enforced server-side; never trust the client. |

## 12. Known Limitations

- Prices and availability shown while browsing are not real (§7.1–7.2); nothing on the Home/Results screens should be read as an actual Rail Europe fare. The one place this app *is* fully real is the checkout handoff (§7.4) — the eurotrain.net page the user lands on shows genuine live prices and can complete a genuine purchase.
- The no-connection gate (§7.5) reflects "connected to a network," not "the internet is genuinely reachable" — this is an inherent limitation of `navigator.onLine`/OS-reported connectivity, not something this app's code can fully close without an active reachability probe (e.g. polling a lightweight endpoint), which was left out to avoid adding a background network dependency of its own to what is otherwise a simple, honest connectivity check.
- Persistence is limited to recent searches (§7.7): closing the app still loses the in-progress search criteria and selected fare (`AppState` is in-memory only, by design — §7.7), and there's no history of past checkout handoffs, only of searches run.
- Localization covers Turkish and English only (§6) — Russian, relevant to the Azerbaijan market per Odamigo's stated TR/CY/AZ markets, isn't in yet; see roadmap.
- No automated test suite (unit/e2e) beyond the manual Playwright smoke-walk used during development — see roadmap.
- Round-trip pricing shows each leg's estimate independently (outbound fare + return fare); it doesn't model real return-fare discounts some rail products offer, since that isn't something the seed pricing engine (§7.2) claims to replicate — the deep-link handoff is where any real discount would actually surface, on eurotrain.net itself.
- `Linking.openURL` on web opens a new browser tab; on a real iOS/Android device it opens the system browser (or eurotrain.net's own app, if one exists and is installed and registered for universal/app links — not something I've confirmed) — this has been verified against the exported web build only, not on-device, for the reason below.
- Only tested on web (Chromium) during development due to this being a headless build environment without a device/simulator attached; TypeScript compiles cleanly and the code uses only cross-platform RN APIs, but native iOS/Android behavior (safe-area insets, gesture conflicts, `Linking.openURL`'s native share sheet) has not been visually verified on-device.
- Live schedule coverage (§7.6) requires the one-time `LIVE_SCHEDULE_REPO` setup in §2 — until that's done, Results always shows the synthetic schedule, clearly labelled as such.
- Live coverage only includes journeys a single physical train covers end-to-end (any two stations one through-service calls at, in order); it does not model connections that require changing trains, so a route like London↔Bruges (the one non-direct route in `routes.ts`) will likely never show live times and will keep using the synthetic generator instead — this is a real, disclosed gap, not a bug.
- Station matching in the live pipeline (`scripts/gtfs-lib.mjs`) is name/keyword-based, not by a documented stop-id mapping (none is published) — verified only against a hand-built synthetic fixture in this sandbox (real feed unreachable here, see §9), so the keyword list may need a small adjustment the first time it runs against the real feed's actual stop names, if Eurostar's naming differs from what was assumed.
- The real-time delay figure is best-effort: it's the first non-zero delay GTFS-RT reports anywhere along that trip, not necessarily the delay at the specific boarding stop shown; platform information, though present in some GTFS-RT feeds, wasn't included since it's non-standard and its exact field wasn't verifiable without reaching the live feed.
- Dates/times in the live pipeline are handled as plain ISO strings without explicit timezone conversion (assumed to already be in the feed's local wall-clock time, which is standard GTFS practice) — this hasn't been verified against the real feed for this reason.
- GitHub Actions' `schedule` trigger is best-effort, not to-the-minute — GitHub explicitly reserves the right to delay scheduled runs during high load, especially on public repos; `live-schedules.json`'s own `generatedAt` timestamp (surfaced in the app's freshness badge) is the honest source of truth for how fresh the data actually is, rather than assuming the cron cadence held exactly.
- Recent searches (§7.7) are capped at 5 entries and store route/trip-type/passenger criteria only, not the date searched (§1) — they persist across an app restart via AsyncStorage, but there's no server-side account, so they don't sync across devices.
- The Help screen's FAQ is static, hand-written content, not a live chatbot or a connection to eurotrain.net's actual support system; its two outbound links (help center, contact form) do go to eurotrain.net's real pages, verified as described in §7.
- The launch animation (§1) runs for a fixed ~2.2s and isn't user-skippable; since it overlays rather than blocks the app underneath (App.tsx), this only affects perceived launch time, not functionality.

## 13. Roadmap

**MVP (this submission)** — one-way and round-trip search with a full Turkish/English UI (§6), quick-date presets and a cheapest-day highlight alongside date/fare comparison, real GTFS-sourced departure times and delays where available (§7.6) with a clearly-labelled synthetic fallback elsewhere, on-device recent searches (§7.7), a trip summary + real eurotrain.net deep-link handoff at checkout (single link, both legs, for a round trip), an in-app Help & contact screen linking out to eurotrain.net's real support pages, a real device-connectivity gate, an animated launch intro, core empty/loading/error states, live FX conversion with fallback.

**Post-MVP** (next, still pre-launch): real Rail Europe partner API integration behind the existing `services/` seam so Results shows genuinely live *prices* too, not just times (the one piece §7.6 couldn't reach — GTFS has no fares); extending live coverage to connecting/interline journeys (currently single-through-train only, §12) by chaining two live legs through a common station; platform/delay data verified and refined against the real feed once reachable (currently designed and unit-tested against a synthetic fixture only, §9); accounts + saved searches ("My Searches" — since there's no in-app booking to retrieve, this would track past handoffs rather than a PNR lookup, and would let recent searches, §7.7, sync across devices instead of staying on-device only); an expanded station/route table (beyond the current 9-station seed) so more origin-destination pairs can deep-link out; seat-class-aware deep-linking (passing the user's Standard/Plus/Premier pick through to eurotrain.net once/if their URL scheme supports it — not yet confirmed); a stronger connectivity check (an active reachability probe, not just `navigator.onLine`/OS state — see §12) once there's a lightweight endpoint worth polling for it; open-jaw trips (returning from a different city than you arrived in — Rail Europe supports this, left out here for the same focus reasons as multi-leg journeys below); push notifications for live train status, now that the underlying real-time delay data (§7.6) already exists to build them on top of; basic analytics on funnel drop-off (search → results → checkout → handoff-click) to validate the core-journey assumption with real users; automated test coverage beyond the live-schedule parser (unit tests on `journeyGenerator`'s pricing logic, `bookingLink`'s URL-building, and `recentSearches`' persistence logic, e2e on the full flow).

**Future**: loyalty/points program; an AI itinerary/trip-planning assistant as an actual end-user feature (deliberately excluded from MVP, §9) — e.g. "help me plan a 4-day Benelux trip" turning into a pre-filled multi-city search, which is a much stronger AI product bet than a generic support chatbot; B2B/travel-agency booking mode for Odamigo's existing customer base; Russian language support to fully cover the TR/CY/AZ markets (TR/EN already shipped in the MVP, §6); an in-app support chat on the Help screen, replacing today's static FAQ + link-out (§12), if usage data showed static content wasn't enough; full accessibility audit beyond the wheelchair-user search flag already in the MVP.
